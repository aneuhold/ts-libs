# Microcycle Regeneration

## Goal

Recompute the planned sets for workouts that have not been logged yet, including those in the microcycle currently in progress. Today `generateOrUpdateMesocycle` refuses: `#cleanUpIncompleteMicrocycles` throws when the first incomplete microcycle has a completed first session, so once a week starts, nothing in it or after it can be replanned.

This depends on the progression fix in `workout-progression-fix-plan.md`. Regenerating before that lands just reproduces the same wrong numbers.

## The shape that fits the existing system

Three observations drive the design.

**The unit is the unlogged session, not the microcycle.** A session is what carries a date and a set of exercises, and "has anything been logged here" is a per-session question. Regenerating a microcycle is then just regenerating each of its unlogged sessions, and regenerating everything after is what the existing mesocycle path already does. Sessions inside a microcycle do not depend on each other: set counts come from the microcycle's set plan and weights come from the previous microcycle's sets for the same exercise, so they can be rebuilt one at a time.

**Regeneration keeps the session's documents and replaces only the numbers.** The session keeps its ID, title, and date. Its `WorkoutSessionExercise` documents stay too, with `setOrder` and `isRecoveryExercise` rewritten. Only sets are deleted and recreated. That means regeneration never needs to know which planned slot a session occupies, which is the ambiguity that caused the original bug and the reason a stored session index came up earlier. It also means regeneration does not repair a microcycle that is missing a session; it fixes numbers, not layout. Repairing layout needs slot identity and is a separate conversation.

**This is not a new pipeline.** It is `generateOrUpdateMesocycle` no longer stopping at a started microcycle. Everything after the current week is already deleted and regenerated by the existing cleanup path.

Together those give the entry point a single rule: **everything not yet logged is regenerated from current data.** No IDs to pass, no selection, no way to produce a half-updated plan.

## On the options considered

- **Provide a microcycle ID.** Not needed as a selector. The first unlogged session already identifies where regeneration starts, and anything earlier is logged history that must not change.
- **Provide a user ID and pick from a list.** Worth doing one level up, at the mesocycle. A user can have more than one active mesocycle, so the script resolves the active one and prints the list rather than guessing when it is ambiguous.
- **Regenerate the most recent microcycle.** Subsumed. The current microcycle is where the first unlogged session lives, so this is what the single rule already does. It is also not dangerous under that rule: logged sessions are never touched, and the dry run shows exactly which sessions change.
- **Regenerate specific days.** Skip it. Regenerating one day and leaving later days alone leaves those later projections computed from numbers that were just superseded. If it turns out to be wanted later, the coherent knob is "from this session onward", not an arbitrary set of days.

## Steps

### Step 1: Move the per-microcycle plan parameters onto the context

File: `packages/core-ts-db-lib/src/services/workout/Mesocycle/WorkoutMesocyclePlanContext.ts`

`generateOrUpdateMesocycle` computes the total microcycle count, the deload index, and the RIR taper inline in its generation loop. Regeneration needs the same values for a microcycle that already exists. Move them to the context as `totalMicrocycleCount`, `isDeloadMicrocycle(microcycleIndex)`, and `getTargetRir(microcycleIndex)`, and have the generation loop use them.

The context also needs to carry deletions and updates, not just creations: add `setsToDelete` and `sessionExercisesToUpdate` next to the existing `...ToCreate` arrays so a regenerating path can record its operations the same way generation does.

### Step 2: Regenerate one session

File: `packages/core-ts-db-lib/src/services/workout/Session/WorkoutSession.service.ts`

Add `regenerateSession` beside `generateSession`. Given an existing session, its set plan, and the target RIR, it walks `sessionExerciseOrder` and for each session exercise records its current sets for deletion, calls `WorkoutSetService.generateSetsForSessionExercise` to build fresh ones, then rewrites `setOrder` and `isRecoveryExercise` and records the session exercise as an update.

The per-exercise body is nearly what `generateSession`'s loop already does, the difference being that one creates the session exercise and the other reuses it. Factor that shared part into a private helper rather than letting two loops drift.

Guard here: a session with any logged set is skipped and reported, never rewritten. `getActiveAndNextSessions` already uses that notion through `#sessionHasLoggedSets`, so promote it to a public `hasLoggedSets`. A partially logged session is left entirely alone rather than having its remaining sets recomputed mid-workout.

### Step 3: Regenerate a microcycle

File: `packages/core-ts-db-lib/src/services/workout/Microcycle/WorkoutMicrocycle.service.ts`

Add `regenerateSessionsForMicrocycle` beside `generateSessionsForMicrocycle`. It computes the set plan once through `WorkoutVolumePlanningService.calculateSetPlanForMicrocycle`, exactly as generation does, then calls `regenerateSession` for each session in `sessionOrder` that has no logged sets.

Note that the recomputed set plan can differ from the one the logged sessions in that microcycle were built with, if volume landmarks moved in the meantime. That is the intended behavior, but it means a week can end up with logged sessions at the old counts and regenerated sessions at the new ones.

### Step 4: Replace the throw

File: `packages/core-ts-db-lib/src/services/workout/Mesocycle/WorkoutMesocycle.service.ts`

In `#cleanUpIncompleteMicrocycles`, a started first-incomplete microcycle no longer throws. It is excluded from the deletions and reported back so `generateOrUpdateMesocycle` can hand it to `regenerateSessionsForMicrocycle` before generating the microcycles that follow. Later microcycles keep being deleted and regenerated exactly as they are today.

The returned `DocumentOperations` then carry the new set deletions and session exercise updates from the context alongside the existing cleanup deletions.

### Step 5: Script

New file: `packages/be-ts-db-lib/scripts/regenerateUserWorkoutPlan.ts`, with a `regenerate:userWorkoutPlan` entry in that package's `package.json`. It follows `getUserWorkoutHistory.ts`: dotenv against `../../.env`, user ID from `process.argv[2]`, `DocumentDb.closeDbConnection` in a `finally`.

- Resolves the active mesocycle (started, not completed). If there is more than one, print them and exit so the caller can pass `--mesocycle <id>`.
- Loads inputs through `buildExerciseCTOsForUser`, `buildMuscleGroupVolumeCTOsForUser`, and the workout repositories.
- Calls `generateOrUpdateMesocycle` and prints, per affected session, the planned sets before and after, plus which sessions were skipped for having logged data.
- Dry run by default. Writes only with `--apply`.

Write order matters: insert the new sets, update the session exercises to point at them, then delete the old sets, so `setOrder` never references a deleted document. Check whether deleting a microcycle already cascades to its sessions, session exercises, and sets through the repository listeners, and if so whether the explicit child deletions in the operations are redundant or harmful.

### Step 6: Tests

- `WorkoutSession.service.spec.ts`: a session with no logged sets is rebuilt and keeps its ID, title, date, and session exercise IDs; a session with logged sets is untouched.
- `WorkoutMicrocycle.service.spec.ts`: a microcycle with a mix of logged and unlogged sessions regenerates only the unlogged ones.
- `WorkoutMesocycle.service.spec.ts`: a started microcycle no longer throws, its unlogged sessions are regenerated, later microcycles are still deleted and recreated, and a fully logged mesocycle produces no operations.

## Validation

Run in `packages/core-ts-db-lib` and `packages/be-ts-db-lib`, or at the root for everything:

```
pnpm check
pnpm test
pnpm lint
```

Then `pnpm regenerate:userWorkoutPlan <userId>` for the dry run, confirm the diff only touches unlogged sessions, apply it, and read the result back with `pnpm get:userWorkoutHistory <userId>`.

## Notes

Running this against real data is only worthwhile after the progression fix lands, and the two overlap in `WorkoutMesocyclePlanContext`, `WorkoutSession.service.ts`, and `WorkoutMesocycle.service.ts`. The overlap is in different parts of those files, but sequencing the progression fix first avoids resolving it twice.

Regeneration deliberately does not restore a session that is missing from a microcycle, since matching a stored session back to a planned slot is exactly the coupling that broke progression in the first place.
